# Юридическая база и ссылки на нормы (Grounded RAG) — дизайн

> Дата: 2026-08-24
> Статус: согласовано с владельцем, ждёт финального ревью спеки перед планом.
> Реестр источников (вход): `docs/legal-base/reestr-istochnikov-prava.md`

---

## 1. Задача

Собрать внутри сервиса «Догодок» юридическую базу российского законодательства, на которую
**ИИ опирается** при работе с договорами, чтобы:
- составлять документы юридически корректно (база работает «за кадром»);
- при проверке/анализе договора показывать **реальные, проверяемые** ссылки на нормы;
- при явном запросе пользователя — вставлять ссылки на статьи и цитаты в текст договора.

Клиенты — широкий спектр (от крупных компаний до самозанятых), но договорное право в РФ
**универсально**: костяк один (ГК и профильные ФЗ), отрасль — тонкий слой сверху.

## 2. Ключевые решения (зафиксированы с владельцем)

| Вопрос | Решение |
|--------|---------|
| Кто потребитель базы | **ИИ** (ссылается на нормы). Пользовательского поиска по законам **нет**. |
| Раздел «поиск по законам» в ЛК | **Не делаем** (YAGNI). |
| Объём v1 | **Универсальное ядро** — ~15 актов (см. §7). |
| Актуальность | **Автосинхронизация по API** pravo.gov.ru, версионирование редакций. |
| Механизм извлечения | **Grounded RAG, гибрид**: полнотекст (Postgres FTS, ru) + вектор (pgvector). |
| Грунтинг | ИИ ссылается **только** на выданные ему нормы; выдуманные — отсекаются. |
| Ссылки/цитаты в тексте договора | Только по **явному запросу** пользователя. По умолчанию договор чистый. |
| Ссылки в проверке/анализе рисков | Показываем норму **по умолчанию** (пользователь сам просит проверку). |
| ПДн | Запрос ретривера строится из **уже замаскированного** текста; в логи — только id/счётчики. |

## 3. Архитектура (обзор)

```
Официальные источники (pravo.gov.ru API / OpenData)
        │  (забор + автообновление)
        ▼
[Ingestion]  seed-core (разовый) + legal-sync worker (BullMQ, регулярно)
        │
        ▼
[Хранилище Postgres]  LegalAct → LegalActEdition (append-only) → LegalNorm (+ FTS + embedding)
        ▲
        │  retrieveNorms()  (гибрид FTS + pgvector, фильтр isCurrent, пред-фильтр по типу договора)
        │
[ИИ-пайплайн lib/ai/tasks]  generate / review / analyze_upload
        │  вставляет «нормативный контекст» в промпт, ИИ ставит маркеры [[norm:id]]
        ▼
[Постобработка]  маркеры → читаемые ссылки на норму + officialUrl (в проверке — по умолчанию;
                 в тексте договора — только по запросу)
```

## 4. Данные (Prisma)

Append-only редакции — в духе правил проекта №1 (версии) и №10 (согласия).

- **`LegalAct`** — акт целиком.
  - `kind` enum: `CODE | FEDERAL_LAW | LAW_RF | REGULATION | GOST` (v1 использует первые три).
  - `number`, `title`, `shortName` («ГК РФ»), `officialUrl`, `sourceSystem` (`pravo.gov.ru`).
- **`LegalActEdition`** — редакция акта, **append-only**.
  - `actId`, `editionDate`, `amendedByRef` (какой акт внёс изменения), `importedAt`,
    `sourceUrl`, `isCurrent` (bool). Правка закона = новая строка, старую не трогаем.
- **`LegalNorm`** — единица поиска и цитирования.
  - `editionId`, `path` («ч.2 ст.454 п.1»), `articleNumber`, `paragraphNumber`, `title`,
    `text`, `fts` (tsvector, русский словарь), `embedding` (vector).
- **`ContractTypeMap`** — маппинг «тип договора → релевантные акты» для пред-фильтра поиска.

Инфраструктура: расширение **pgvector** в Postgres (добавить в `docker-compose`), индексы:
GIN на `fts`, IVFFlat/HNSW на `embedding`.

## 5. Наполнение и синхронизация

### 5.1 Сидер ядра — `scripts/legal/seed-core.ts` (разовый)
Импорт актов ядра из официального структурированного текста, нарезка на нормы по
статьям/пунктам, расчёт эмбеддингов, запись первой редакции (`isCurrent=true`).

### 5.2 Воркер `legal-sync` (BullMQ, регулярно) — в стиле `generate-document`
1. Опрос API `publication.pravo.gov.ru` / OpenData на акты, изменяющие отслеживаемые.
2. При обнаружении → задача «перезагрузить консолидированный текст акта».
3. Создаётся **новая `LegalActEdition`**, пересчёт норм и эмбеддингов; прежняя редакция → `isCurrent=false`.

### 5.3 Честный компромисс по консолидации (главный риск)
API отдаёт отдельные акты «о внесении изменений», а не склеенный текст кодекса. Автоматически
вклеить поправку в текст — сложно. В v1:
- детект факта изменения по API → повторная загрузка **консолидированного** текста акта из ИПС;
- где чистого консолидированного текста получить нельзя — **флаг «нужна ручная проверка»** в
  админку `/admin`, а не молчаливая устаревшая норма.

## 6. Извлечение и интеграция в ИИ-пайплайн

### 6.1 Модуль `lib/legal/retrieval.ts`
`retrieveNorms({ contractType, clauses, topK })`:
- гибрид: Postgres FTS (ru) + pgvector cosine, слияние и ре-ранк;
- фильтр `isCurrent = true`; пред-фильтр по `ContractTypeMap`;
- **graceful fallback**: если эмбеддинг-оператор недоступен — только FTS.

### 6.2 Точки вызова (`lib/ai/tasks`)
- **`generate`** — база используется «за кадром» для корректности. Ссылки/цитаты в текст —
  только если пользователь явно просил (флаг запроса).
- **`review` / `quick_analysis`** — нормы показываем по умолчанию: «норма → риск/что проверить».
- **`analyze_upload`** — то же, что review, для загруженного документа.

### 6.3 Промпт-контракт и защита от галлюцинаций
- В промпт добавляется блок «Нормативный контекст — ссылайся только на него, по id».
- Модель ставит маркеры `[[norm:<id>]]`.
- Постобработка меняет маркеры на читаемую ссылку + `officialUrl`. Норму, которой нет в
  выданном контексте, помечаем как непроверенную/убираем.

### 6.4 Эмбеддинги через мультиоператор
Новая ИИ-задача `embed` в существующем роутере (`lib/ai`), провайдер — GigaChat/OpenRouter
Embeddings. Ложится в текущую схему операторов и usage-логов.

## 7. Объём ядра v1 (~15 актов)

ГК ч.1–4 · ТК РФ · НК ч.1–2 · Закон «О защите прав потребителей» (2300-1) · 152-ФЗ (ПДн) ·
44-ФЗ · 223-ФЗ · 422-ФЗ (НПД/самозанятые) · 14-ФЗ (ООО) · 208-ФЗ (АО) · 38-ФЗ (реклама) ·
402-ФЗ (бухучёт) · 173-ФЗ (валютное регулирование).

Покрытие: ~80–90% реальных договоров любой сферы. Отраслевые акты (техрегламенты, отраслевые
ФЗ, ГОСТ) — **докладываются по требованию**, когда такие договоры реально появятся.

## 8. Приватность и логи

- Ретривер получает **уже замаскированный** текст (ИНН/счета/паспорт маскируются перед ИИ) —
  реквизиты не уходят в эмбеддинг-провайдер.
- Правило №11: в логи идут только id норм, счётчики, коды ошибок — не текст норм и не
  содержимое договоров.

## 9. Монетизация

Отдельной платы за юридическую базу нет — это внутренний слой качества существующих ИИ-задач
(`generate`/`review`/`analyze_upload`), которые уже тарифицируются токенами. Явная вставка
ссылок/цитат по запросу — в рамках уже оплаченного ИИ-действия (правок/проверки).

## 10. Открытые вопросы / риски

1. **Консолидация текста** (§5.3) — основной риск, решается semi-auto + флаг ручной проверки.
2. **Доступность эмбеддинг-оператора** — нужен рабочий провайдер; иначе FTS-only.
3. **Формат структурированного текста ядра** — уточнить на этапе плана: откуда берём чистый
   текст ГК/ФЗ, разбитый по статьям (ИПС `pravo.gov.ru/ips`, OpenData, либо разовый ручной
   импорт для ~15 актов).
4. **Объём хранилища** — десятки тысяч норм + эмбеддинги; для Postgres некритично, оценить на плане.

## 11. Вне рамок v1

- Пользовательский поиск по законам / раздел в ЛК.
- Судебная практика, ведомственные разъяснения, ГОСТ, подзаконка (последующие фазы).
- Автоматический «умный» merge поправок в текст кодекса.
- Коммерческие СПС (КонсультантПлюс/Гарант).
