# Нумерация договоров по юрлицам — дизайн

Дата: 2026-08-17
Статус: согласовано, готово к реализации

## Задача

У пользователя в системе несколько собственных юрлиц (`Profile`). У каждого своя
принятая в делопроизводстве форма номера договора: `05/08-26`, `ДГ-001/2026`,
`17/03` и т.д. Сейчас `Document.number` — свободная строка, которую пользователь
каждый раз набивает руками, автонумерации нет вообще, а поиск по номеру не работает.

Нужно:

1. Задавать формат номера в карточке своего юрлица.
2. При создании договора и при загрузке готового Word-файла предлагать следующий
   номер по этому формату, с возможностью вписать свой.
3. Искать документ по номеру.

## Текущее состояние (что выяснено разведкой)

| Факт | Файл |
|---|---|
| `Document.number String?` — свободный текст, без индекса и уникальности | `apps/web/prisma/schema.prisma:206` |
| Четыре независимые точки ручного ввода номера | мастер `documents/new/page.tsx:1039`, «Параметры документа» `documents/page.tsx:158`, две модалки подписания `documents/page.tsx:255` и `documents/[id]/page.tsx:79` |
| Автонумерации `Document.number` нет | — |
| `documentNumber Int?` — отдельное поле, порядковый номер приложения/ДС, автонумерация `MAX+1` есть | `api/documents/route.ts:136-145` |
| Поиск `q` идёт **только по `title`** | `api/documents/route.ts:63` |
| Экран загрузки Word не передаёт `profileId` | `documents/upload/page.tsx:586-600` |
| «Активного профиля» в модели нет, везде берётся `data[0]` | `documents/new/page.tsx:1353` |
| Номер попадает в Word только при скачивании, в предпросмотре его нет | `html-docx-converter.ts:678` vs `html-document.ts:707` |

Известные баги, которые чиним попутно:

- Мастер при выборе родительского договора кладёт порядковый номер приложения в
  текстовое поле `number` (`documents/new/page.tsx:925-931`), из-за чего у
  приложения оказываются два разных номера: `number = "3"` и `documentNumber = 1`.
- Тот же код запрашивает `GET /api/documents?parentDocumentId=…`, но роут этот
  фильтр не поддерживает, поэтому максимум считается по чужой выборке.

## Решения

### Формат — шаблон с плейсхолдерами

Одно текстовое поле в карточке юрлица. Пользователь пишет маску, рядом живой
предпросмотр.

Плейсхолдеры:

| Плейсхолдер | Значение | Пример |
|---|---|---|
| `{N}` `{NN}` `{NNN}` `{NNNN}` | счётчик, число знаков = число букв N (ведущие нули) | `5`, `05`, `005` |
| `{ГГГГ}` / `{YYYY}` | год полностью | `2026` |
| `{ГГ}` / `{YY}` | год двумя цифрами | `26` |
| `{ММ}` / `{MM}` | месяц двумя цифрами | `08` |
| любой другой текст | подставляется как есть | `ДГ-`, `/`, `№` |

Латинские алиасы принимаются и нормализуются к кириллице при сохранении — иначе
пользователь упрётся в неразличимые на глаз `М` и `M`.

Шаблон обязан содержать ровно один счётчик. Пустой шаблон = нумерация для этого
юрлица выключена, поле номера ведёт себя как сегодня (свободный ввод).

### Счётчик не храним

Состояние = сами документы. Следующий номер вычисляется обратным разбором:
шаблон превращается в regex, где дата зафиксирована текущим периодом, а счётчик —
capture-группа. Из номеров документов этого юрлица достаём совпавшие, берём `max + 1`.

Почему не таблица `lastValue`:

- пользователь вписал номер руками → система продолжит с него, хранимый счётчик об этом не узнает;
- отменили создание документа → номер не «сгорел»;
- поменяли шаблон в середине года → пересчёт происходит сам;
- нет рассинхрона БД и реальности.

Цена: `O(число документов юрлица)` на каждый расчёт. При десятках тысяч документов
на юрлицо это придётся пересмотреть; для целевой аудитории (ИП, малые компании) —
несущественно.

### Сброс счётчика выводится из шаблона

| В шаблоне есть | Область счёта |
|---|---|
| `{ММ}` | внутри месяца |
| только `{ГГ}` или `{ГГГГ}` | внутри года |
| ни года, ни месяца | сквозной, навсегда |

Отдельной настройки «сброс» нет. Комбинация «шаблон без года + ежегодный сброс»
породила бы одинаковые номера в разные годы, поэтому такой возможности не даём.

Дата, от которой считается период: `Document.signingDate`, если задана, иначе текущая.

### Приложения и допсоглашения

Наследуют номер родительского договора и собственный счётчик юрлица не тратят.
Заголовок вида «Приложение № 1 к Договору № 005/08-26» уже строится
`buildChildDocPreambleHtml` (`html-document.ts:728`) — нужно лишь перестать
затирать `Document.number` порядковым номером.

### Загрузка Word — номер из текста не извлекаем

Два варианта на выбор: следующий по порядку или свой номер вручную.

### Дубликаты — предупреждение, не запрет

Уникального индекса не ставим. При вводе занятого номера показываем жёлтую плашку
со ссылкой на существующий документ. Сохранить можно.

## Архитектура

### Ядро: `apps/web/src/lib/document-number.ts`

Чистый модуль. Без Prisma, без React, без сети — только строки и даты.

```ts
type FormatError = { code: 'EMPTY' | 'NO_COUNTER' | 'MANY_COUNTERS' | 'UNKNOWN_TOKEN'; message: string }
type Scope = 'month' | 'year' | 'global'

normalizeFormat(tpl: string): string          // латиница → кириллица
validateFormat(tpl: string): FormatError | null
formatScope(tpl: string): Scope
renderNumber(tpl: string, seq: number, date: Date): string
buildMatcher(tpl: string, date: Date): RegExp // дата зафиксирована, счётчик — группа
nextNumber(tpl: string, existing: string[], date: Date): string
```

Разбор шаблона — один проход по строке с выделением токенов `{...}`; всё
остальное экранируется как литерал. Ошибочный плейсхолдер не молчит, а возвращает
`UNKNOWN_TOKEN` — иначе пользователь получит номер с `{ГОД}` внутри.

### Данные

Одна колонка, миграция `add_profile_contract_number_format`:

```prisma
model Profile {
  contractNumberFormat String?   // "{NNN}/{ММ}-{ГГ}"
}
```

Плюс индекс под поиск и расчёт следующего номера:

```prisma
@@index([profileId, number])   // на Document
```

### API

| Метод | Что |
|---|---|
| `GET /api/profiles/:id/next-number?date=YYYY-MM-DD` | `{ format, next, scope, sample }`; `format: null` если нумерация не настроена |
| `GET /api/documents/number-check?profileId=&number=` | `{ conflict: { id, title, counterpartyName } \| null }` |
| `POST/PUT /api/profiles` | принимает `contractNumberFormat`, валидирует через `validateFormat` |
| `GET /api/documents?q=` | поиск расширяется на `number`: `OR: [title, number]` |
| `GET /api/documents?parentDocumentId=` | новый фильтр (починка бага) |

Все роуты скоупятся по `userId`, как остальные (правило 9 в `CLAUDE.md`).

### UI

Один общий компонент `apps/web/src/components/document-number-field.tsx`:

```
Номер договора
 ◉ Следующий по порядку — 005/08-26
 ○ Свой номер            [__________]
```

Props: `profileId`, `signingDate`, `value`, `onChange`, `documentId?` (чтобы
исключить себя из проверки дублей). Сам ходит за `next-number` и `number-check`,
сам показывает жёлтое предупреждение о дубле. Если у юрлица формат не задан —
вырождается в обычное текстовое поле.

Точки подключения:

| Экран | Изменение |
|---|---|
| `/requisites` → `ProfileForm` | блок «Нумерация договоров»: поле шаблона, предпросмотр, подсказка плейсхолдеров, «Следующий номер» |
| `/documents/new` шаг 1 | поле «Номер» → `DocumentNumberField`; для APPENDIX/AMENDMENT скрывается |
| `/documents/upload` | добавляется выбор своего юрлица + `DocumentNumberField`; `profileId` начинает уходить в `POST /api/documents` |
| `/documents` список | серверный поиск по номеру, плейсхолдер «Поиск по названию или номеру», сортировка по колонке `№` |
| `EditDocumentModal`, обе `SignModal` | `DocumentNumberField` вместо голого инпута |

## Что в объём не входит

- **Номер в шапке договора.** Сейчас `buildContractPreambleHtml` номер не
  принимает, поэтому в предпросмотре его нет, а в Word он появляется только при
  скачивании. Расхождение остаётся, чиним отдельной задачей.
- **Тесты.** В проекте нет тестового раннера; решено не заводить. Проверка —
  ручная в браузере по сценарию ниже.
- Извлечение номера из текста загруженного файла.
- Жёсткая уникальность номеров.
- Отдельные шаблоны для приложений и допсоглашений.

## Сценарий ручной проверки

1. В `/requisites` у юрлица А задать `{NNN}/{ММ}-{ГГ}` → предпросмотр `001/08-26`.
2. У юрлица Б задать `ДГ-{NN}/{ГГГГ}` → предпросмотр `ДГ-01/2026`.
3. Создать договор от А → предложен `001/08-26`, сохранить.
4. Создать ещё один от А → предложен `002/08-26`.
5. Создать договор от Б → предложен `ДГ-01/2026` (счётчики независимы).
6. Создать от А, выбрать «Свой номер», вписать `010/08-26`.
7. Создать ещё от А → предложен `011/08-26` (продолжил с ручного).
8. Вписать `010/08-26` повторно → жёлтое предупреждение со ссылкой, сохранение проходит.
9. Загрузить Word от юрлица А → предложен следующий номер, выбрать «свой», вписать старый.
10. Создать договор с датой подписания в следующем месяце → счётчик начинается заново.
11. В списке документов найти `010/08-26` через поиск → выдан ровно нужный договор.
12. Создать приложение к договору → `Document.number` не затирается, заголовок
    «Приложение № 1 к Договору № 001/08-26».
13. У юрлица без формата поле номера остаётся свободным текстовым.
