# Задачи после переноса точного предпросмотра (docx-preview)

> Накопленные замечания владельца по итогам живого теста 2026-08-20.
> Правки **не внесены** — это список к работе. Причины уже установлены по коду,
> расследовать заново не нужно.

## Готово (выложено на прод)

- Точный предпросмотр docx-preview на рабочем экране; «Просмотр» ↔ «Редактировать».
- Оригинальный `.docx` сохраняется при загрузке (`Version.filePath`).
- Скачивание = предпросмотр (общий `fetchCurrentDocx`) — ручные правки попадают в файл.
- «Сохранить как версию» не закрывает экран, версии копятся фоном.
- Заголовки разделов больше не синие (явный `color: '000000'` в стилях DOCX).
- Цвет шрифта (чёрный/красный/зелёный/синий) и жёлтая заливка в тулбаре;
  переносятся в Word (`w:color` / `w:shd`), тесты `tests/color-marks.test.ts`.
- Памятка при первой правке (закрывается только крестиком).

## 1. Шапка загруженного договора подменяется нашей ⚠️ приоритет

**Что видит владелец:** загрузил договор с полной готовой шапкой — система показала
**свою** шапку вместо исходной.

**Причина (by design, но нежелательно):**
`getPresentationContent` (`apps/web/src/lib/presentation-content.ts:164`) для
загруженных документов (`looksLikeUpload`) вызывает `replaceDocumentPreamble` и
подменяет шапку эталонной из ЛК (`getReferenceBlocks` → `buildContractPreambleHtml`).

**Что решить:** для загруженных документов шапку из файла **не трогать** (пользователь
уже принёс готовую), либо сделать подмену явным действием через шаг «Оформление».
Учесть: `Document.preambleHtml` имеет приоритет, если владелец правил шапку в мастере.

## 2. Пропал заголовок «ДОГОВОР № …» по центру

**Что видит владелец:** в шапке нет строки «ДОГОВОР № X» сверху по центру.

**Причина (подтверждена):** `buildContractPreambleHtml`
(`apps/web/src/lib/html-document.ts:777`) собирает только мета-строку (город/дата) и
абзац представления сторон — **заголовка документа в ней нет**. Для приложений и
допсоглашений заголовок есть (`buildChildDocPreambleHtml` → `doc-preamble-title`),
для основного договора — нет.

**Что сделать:** добавить в шапку основного договора строку заголовка
(`ДОГОВОР № {Document.number}` + тип документа), по образцу `buildChildDocPreambleHtml`.
Номер и дата уже есть в `Document.number` / `Document.signingDate`.

## 3. Подписант контрагента не подтянулся в шапку ⚠️ приоритет

**Что видит владелец:** в шапке «в лице \_\_\_\_\_, действующего на основании \_\_\_\_\_»,
хотя в карточке контрагента подписант заполнен (президент, устав, ФИО).

**Причина (подтверждена — расхождение двух путей):**
- шапка предпросмотра: `getReferenceBlocks` (`presentation-content.ts:46`) берёт
  подписанта строго `where: { isDefault: true }`;
- скачивание: `resolveCounterpartySignatory` (`lib/party-data.ts:38`) берёт с
  фолбэком — `orderBy: [{ isDefault: desc }, { createdAt: asc }]`.

Если подписант **не помечен «по умолчанию»**, шапка получает прочерки, хотя данные есть.
`buildPartyPreambleParts` (`html-document.ts:758`) на пустой `signatorName` рисует
`_____________`.

**Что сделать:** перевести `getReferenceBlocks` на `resolveCounterpartySignatory`
(единый резолвер), чтобы предпросмотр, шапка и DOCX брали одного подписанта.

## 4. ИИ правит шапку, хотя не должен

**Что видит владелец:** после точечной правки пункта ИИ переписал и шапку.

**Причина:** чат (`app/api/versions/[id]/chat/route.ts`) отдаёт `editDocument` весь
документ вместе с шапкой. Защита `stripAiPreamble` существует, но применяется только
в генераторе (`lib/queue.ts:196`), не в чате.

**Важно (проверено):** роль пользователя ИИ знает **не из шапки**, а из
`settings.customInstruction` («Пользователь является исполнителем/заказчиком. Защищай
его интересы») + `protectionLevel` — см. `gigachat-provider.ts:737`. Поэтому отрезать
шапку от правки безопасно, защита интересов не пострадает.

**Что сделать:** в режиме `edit` отрезать шапку перед отправкой ИИ и возвращать её
на место после ответа — как уже сделано с блоком реквизитов. Дополнительно передать
ИИ явные роли сторон по именам (из карточек ЛК), чтобы он не путал термины в пунктах.

## 5. Нумерация сбивается после ИИ-правки

**Что видит владелец:** вставленный пункт получил «1.3», следующий тоже остался «1.3».

**Причина:** блочный движок правок (`lib/doc-blocks.ts` + промпт перенумерации в
`editDocument`) не пересчитывает номера соседних подпунктов при вставке/удалении.

**Что сделать:** после применения блочных операций пересчитывать нумерацию подпунктов
внутри раздела и подтягивать перекрёстные ссылки на них.

## 6. Не видно маркеров («точек») в маркированных списках ⚠️ фикс на 2 строки

**Что видит владелец:** пункты списка сдвинуты отступом, но самой точки-маркера нет
(функция списка работает, маркер не рисуется).

**Причина (подтверждена):** Tailwind v4 preflight сбрасывает маркеры глобально —
`ol, ul, menu { list-style: none; }` (`node_modules/tailwindcss/preflight.css:197`).
В стилях редактора (`app/globals.css:473`) для `.document-viewer ul` задан только
`padding-left: 22px`, а `list-style` обратно **не возвращается**. Отсюда ровно то, что
видно: отступ есть, маркера нет.

Нумерованные списки не пострадали — у них свои маркеры через CSS-счётчики
(`ol.ol-legal > li::before`), но `<ol>` **без** класса `ol-*` останется без номеров
по той же причине.

**Что сделать:** вернуть `list-style: disc` (+ `list-style-position: outside`) для
`.document-viewer ul` / `.ProseMirror ul`; проверить `<ol>` без класса.
Отдельно убедиться, что маркеры доходят до DOCX (в Word — свой список, не CSS).

## 7. В режиме просмотра пропадает красный текст (заливка при этом видна) ⚠️

**Что видит владелец:** в режиме «Просмотр» (docx-preview) жёлтая заливка есть, а
красный текст стал чёрным. Маркеры списка в просмотре, наоборот, появляются — потому
что там рисует Word-разметка, а не CSS редактора (см. п.6).

**Причина (подтверждена экспериментом):** цвет теряется на формате записи.
- Кнопка ставит цвет как `#C81E1E`, но TipTap читает его обратно из DOM —
  `element.style.color` (`@tiptap/extension-text-style`), а браузер **нормализует**
  значение в `rgb(200, 30, 30)`.
- `docxColor()` в `packages/shared/src/formatting/html-docx-converter.ts` понимает
  только `#hex` и словарь имён — формат `rgb()` возвращает `undefined`, и цвет в
  DOCX не попадает.
- Проверено тестом: `<span style="color: #C81E1E">` → `w:color` есть;
  `<span style="color: rgb(200, 30, 30)">` → `w:color` **отсутствует**.

**Почему заливка уцелела:** у `<mark>` в конвертере есть запасной вариант — если цвет
не распознан, ставится жёлтый `FFF176` по самому тегу. Поэтому подсветка видна, а
цвет шрифта нет.

**Что сделать:** научить `docxColor()` разбирать `rgb()/rgba()` (и заодно
`hsl()`, если встретится). После этого цвета и заливки будут видны и в режиме
просмотра, и в скачанном Word — отдельного механизма для предпросмотра не нужно,
он рисует тот же `.docx`. Добавить тест на `rgb()` в `tests/color-marks.test.ts`.

## 8. Памятка о переформатировании не появляется ⚠️

**Что видит владелец:** окошко с крестиком, предупреждающее, что после правок
документ переформатируется, — не показывается вообще.

**Что уже проверено (чтобы не искать заново):**
- разметка памятки **есть в собранном бандле**
  (`.next/static/chunks/*.js` содержит текст «переводится в рабочий формат»),
  значит код доезжает до браузера, и деплой ни при чём;
- `noteDocumentEdited()` вызывается из обоих путей правки —
  `onUpdate` редактора (`work/page.tsx:1404`) и ИИ-правки (`work/page.tsx:800`);
- логика показа корректна: ref-флаг → `setReformatNoticeOpen(true)`;
- блок рендерится на верхнем уровне фрагмента, не внутри чужого условия;
- «обрезающего» предка нет: `main` в `AppLayout` — `overflow-y-auto` без
  `transform/filter/contain`, то есть `position: fixed` привязан к окну и не
  обрезается. Мобильный drawer с `transition-transform` — соседний узел (`md:hidden`).

**Оставшиеся версии причины (проверять в браузере):**
1. Позиционирование `right: 436; bottom: 20` уводит окно в неудачное место на
   конкретной ширине экрана (например, за панель чата или ниже видимой области).
2. Памятка появляется, но визуально теряется на фоне документа (низкий контраст,
   угол вне зоны внимания).

**Что сделать:** вместо угла показывать памятку **явной полосой над документом**
(там же, где панель режима «Просмотр/Редактировать») — с крестиком, как просил
владелец. Это снимает любые вопросы позиционирования и попадает в зону внимания.
Проверить в браузере на реальном документе, а не только по коду.

## 9. Чат отвечает «Готово», ничего не сделав, и списывает правку ⚠️ приоритет

**Что видит владелец:** в режиме «Правка» попросил «Проверь документ на наличие
ошибок». Через несколько минут ответ: «Готово — изменения внесены в документ».
Фактически: пункт 1.3 (чужой, не относящийся к договору) не тронут, дубль нумерации
1.3 / 1.3 не исправлен, ошибки в суммах приложения не исправлены. Содержательного
ответа нет. При этом **правка списалась из пакета** (на экране «Правок осталось: 9 из 10»).

**Причина (подтверждена):** в `apps/web/src/app/api/versions/[id]/chat/route.ts:199`
ответ пользователю — **захардкоженная строка**:
```ts
// Простое подтверждение без лишнего AI-запроса
const explanation = 'Готово — изменения внесены в документ.'
```
Она отправляется всегда, когда ИИ вернул непустой документ. Сравнения «до/после»
нет, перечня внесённых изменений нет. Правка при этом уже зарезервирована в пакете;
возврат (`releaseEdit`) происходит только при ошибке или `__EDIT_FAILED__`, но не в
случае «ИИ вернул документ без изменений».

Отдельно: запрос «проверь на ошибки» — это по смыслу **анализ**, а не правка. В
режиме «Правка» блочный движок пытается применить операции; если менять нечего,
документ возвращается как есть — и пользователь получает ложное «Готово».

**Что сделать:**
1. Сравнивать документ до и после. Если не изменился — не писать «Готово», честно
   сообщить, что правок не внесено и почему, и **вернуть правку в пакет**
   (`releaseEdit`), чтобы не списывать деньги за пустой результат.
2. Давать содержательную обратную связь: перечень того, что изменено (блочный движок
   знает применённые операции — `applyBlockOps` возвращает результат), а если часть
   запроса не выполнена — сказать, что именно и почему.
3. Запросы вида «проверь на ошибки / найди ошибки» в режиме «Правка» распознавать и
   либо выполнять как анализ с текстовым ответом, либо предлагать кнопку
   «Анализ»/«Риски», а не изображать правку.

## 10. Вопросы к ИИ бесплатны и безлимитны — дыра в монетизации ⚠️ приоритет

**Что видит владелец:** загрузил Word, поправил руками, скачал. Задал правку через
чат — токены не списались (правок ИИ фактически не внёс — это как раз правильно).
Затем переключился на «Вопрос» и попросил проверить документ на ошибки — ИИ
просканировал весь договор и выдал подробный разбор. **Токены снова не списались.**
Пользователь получил серьёзную работу ИИ по загруженному документу бесплатно.

**Причина (подтверждена):** в `app/api/versions/[id]/chat/route.ts` вызов
`chargeTokens` стоит **только** внутри ветки `data.mode === 'edit'` (строка 92).
Режимы `chat` и `quick_analysis` не тарифицируются и не имеют квоты вообще.

Текущие точки списания (для сверки):
| Действие | Списание |
|---|---|
| Генерация с нуля | `generate` = 100 |
| Первая правка загруженного | `uploadEditStart` = 50 (даёт пакет из 10 правок) |
| «Переписать заново» | `rewrite` = 100 |
| Докупка пакета правок | `editPackage` = 100 |
| «Риски» (проверка версии) | `review` = 25 |
| Анализ при загрузке файла | `analyzeUpload` = 25 |
| **Режим «Вопрос» в чате** | **нет** |
| **Кнопка «Анализ» в чате** | **нет** |

Отдельная несогласованность: «Риски» стоят 25 токенов, а кнопка «Анализ» в чате
делает близкую по смыслу работу **бесплатно**.

**Что решил владелец (принцип):** любое **первое** применение ИИ к документу должно
быть предоплачено. Ручные правки — всегда бесплатны.

Вариант A (предпочтительный — «предоплата + пакет»):
- пользователь платит за первое ИИ-действие с документом (генерация с нуля /
  старт работы с загруженным);
- после оплаты получает пакет: N ИИ-правок **или** N вопросов бесплатно;
- вопросы и «Анализ» тратят тот же пакет, что и правки, и требуют его наличия;
- если пакета нет — предложить оплату, а не отвечать бесплатно.

Вариант B (запасной, если пакетная схема не ложится): поштучная тарификация
каждого ИИ-действия — генерация ~100, каждая правка ~2–10, каждый вопрос ~5–10;
ручное редактирование бесплатно всегда.

**Технические требования:** цены только через `lib/token-pricing.ts` / ENV
`TOKEN_PRICE_*` (правило проекта №4); списание и проверка баланса атомарны
(`chargeTokens`, SELECT FOR UPDATE); при сбое ИИ — возврат (`refundChargeById`).
Не забыть показать цену на кнопках/в интерфейсе чата, как сделано для правок.

## 11. Индикаторы лимитов противоречат друг другу и обрезаются

**Что видит владелец:** в строке под чатом одновременно —
«Правок осталось: 9 из 10» и «Первая правка · 50 то…» (обрезано). Утверждения
взаимоисключающие: если осталось 9 из 10, первая правка уже сделана.

**Причины (подтверждены, их две):**
1. **Верстка:** это два независимых индикатора в одной строке
   (`work/page.tsx:1575` и `:1578`), условия показа пересекаются, ширины не
   хватает — правый текст обрезается.
2. **Устаревшее состояние:** после правки сервер шлёт по SSE только
   `editsRemaining` / `editsLimit`, и локально обновляются лишь `remaining`,
   `limit`, `used` (`work/page.tsx:774`). Поле **`packages` не обновляется** и
   остаётся прежним (0), а плашка «Первая правка» показывается именно по
   `packages === 0` — поэтому она продолжает висеть после первой правки.

**Что сделать:** показывать **один** индикатор состояния пакета (взаимоисключающие
ветки, а не два `<span>` рядом), не допускать обрезки текста; обновлять квоту после
правки целиком — либо присылать `packages` в событии `done`, либо перезапрашивать
`/api/documents/{id}/edit-quota` (`refreshQuota()` уже есть).

Учесть при работе над п.10: если вопросы станут платными, индикатор должен
показывать и остаток вопросов — тем более важно свести всё в одну понятную строку.

## 12. Режим «Вопрос»: ответы-простыни, ИИ переписывает документ в чат ⚠️

**Что видит владелец:** на вопрос «найди ошибки в приложении» ИИ переписал в чат
всю таблицу приложения — со всеми позициями, ценами и суммами. Помимо нечитаемости
это **дыра**: пользователь может попросить «перепиши пункт целиком», получить готовый
текст в чате бесплатно и вставить его в свой договор мимо платных правок.

**Причина (подтверждена):** системный промпт режима «Вопрос»
(`buildSystemPrompt`, `apps/web/src/lib/ai/gigachat-provider.ts:41`) состоит из пяти
общих строк про стиль юриста. В нём **нет**:
- ограничения на длину ответа;
- запрета цитировать/переписывать документ или таблицы целиком;
- требования отвечать по схеме «где → что не так → почему».

Дополнительно `max_tokens: 32768` (`chat`, строка 604) прямо разрешает простыни.

**Что сделать:** переписать промпт режима «Вопрос»:
- отвечать сжато и по делу: место (номер пункта/строки), суть проблемы, причина,
  что делать;
- **запрет** воспроизводить текст договора и таблицы целиком; цитировать только
  короткий фрагмент, необходимый для указания на проблему (например, до 15 слов);
- на просьбы «перепиши пункт / составь текст» — не выдавать готовый текст в чат,
  а направлять в режим «Правка» (это платное действие);
- снизить `max_tokens` до разумного для ответа в чате.

Связано с п.10: когда вопросы станут платными, это перестанет быть бесплатным
обходом, но ограничение на выдачу готового текста всё равно нужно.

## 13. ИИ не проверяет суммы построчно — «плоско» смотрит на итог ⚠️

**Что видит владелец:** намеренно внёс ошибки в отдельные ячейки таблицы приложения.
ИИ посмотрел итоговые суммы, сказал, что всё верно, потом начал противоречить себе и
спрашивать у пользователя, где именно внесены ошибки. Построчно (Кол-во × Цена ×
Коэффициент = Сумма) не считал, промежуточные итоги по разделам не сверял.

**Причины (подтверждены, их две):**
1. **Нет арифметической методики в промпте.** `buildSystemPrompt` не содержит
   никаких правил проверки расчётов — модель просто «читает» таблицу. Для сравнения:
   в редактировании таблиц правило есть явно
   (`gigachat-provider.ts:638`: «Сумма = Кол-во × Цена; строка ИТОГО = сумма всех
   строк»), а в режиме вопросов — нет.
2. **Приложения могут вообще не попадать в анализ.** В `review` документ длиннее
   40 000 символов обрезается, причём специально по началу приложений
   (`gigachat-provider.ts:975`): в текст подставляется
   «[Приложения к договору не включены в анализ…]». То есть ошибки в приложении там
   не могут быть найдены в принципе.

**Что сделать:**
- добавить в промпт вопросов/анализа явный алгоритм для таблиц: пересчитать каждую
  строку, сверить с указанной суммой, просуммировать строки по разделу, сверить с
  «Итого», затем сверить общий итог; расхождения выводить списком
  «строка → ожидалось → указано»;
- не спрашивать у пользователя, где ошибки, — находить самому;
- пересмотреть обрезку приложений: для вопросов по приложению анализировать именно
  приложение (или считать таблицы кодом, а не моделью — арифметика детерминирована и
  дешевле/надёжнее в коде);
- если модель не тянет — сменить её для задач `chat` / `quick_analysis` в админке
  `/admin/ai` (маршрут задачи → оператор + модель, `getActiveModelId(task, …)`),
  код менять не требуется.

> Заметка: точный пересчёт таблиц лучше делать **в коде** (детерминированно), а модели
> оставить формулировку выводов. Это надёжнее любой смены модели.

## 14. Ответы в чате идут сплошным текстом без абзацев

**Что видит владелец:** ответ ИИ — сплошная стена текста. Даже нумерованный список
(«1. Пересчитаю… 2. Сравню… 3. Напишу…») склеивается в одну строку, непонятно, где
заканчивается одна мысль и начинается следующая.

**Причина (подтверждена, техническая):** ИИ присылает текст с переносами строк, но
пузырь чата рендерит его как обычный текст в `<div>`
(`work/page.tsx:104` — `{isUser ? msg.content : stripMarkdown(msg.content)}`).
HTML по умолчанию **схлопывает переносы строк в пробел**, а `white-space: pre-wrap`
у пузыря не задан — поэтому вся структура ответа теряется на отрисовке.

Усугубляет `stripMarkdown` (`work/page.tsx:111`): она вырезает заголовки, жирный,
курсив и **маркеры списков** (`^[-*]\s+`), то есть последние признаки структуры,
ничего не давая взамен.

**Что сделать:** отображать структуру ответа —
- минимально: `white-space: pre-wrap` на пузыре ИИ (сразу вернёт абзацы и списки);
- лучше: аккуратно рендерить простую разметку — абзацы, маркированные и нумерованные
  списки, жирный — вместо полного вырезания markdown;
- в промпте (см. п.12) попросить отвечать короткими абзацами/списком, а не
  «полотном».

## 15. Панель чата перегружена: «щит 60» и всегда развёрнутые быстрые команды

Правая колонка узкая, и её низ занят элементами, которые мешают работе.

### 15.1. Иконка щита с числом — убрать

**Что видит владелец:** в поле ввода слева иконка щита и «60». Непонятно, что это и зачем.

**Причина (подтверждена):** это `protectionLevel` — уровень защиты интересов из
настроек ИИ (`work/page.tsx:1617–1621`). Отрисован **кнопкой без `onClick`** — то
есть ни на что не нажимается и ничего не делает; смысл раскрывается только в
`title` при наведении мышью («Уровень защиты: 60%»), чего пользователь не видит.

**Что сделать:** убрать элемент из поля ввода. Если уровень защиты нужно показывать —
его место в настройках документа/версии, а не в строке ввода сообщения.

### 15.2. Быстрые команды — спрятать под кнопку

**Что видит владелец:** пять чипов («Добавить неустойку», «Усилить
конфиденциальность», «Уточнить сроки оплаты», «Добавить форс-мажор», «Передача прав
на ИС») всегда развёрнуты и съедают три строки в и без того узкой колонке. То же
самое на вкладке «Вопрос».

**Причина:** `work/page.tsx:1605` — списки `QUICK_CHIPS_EDIT` / `QUICK_CHIPS_CHAT`
рендерятся всегда, без сворачивания.

**Что сделать:** свернуть их за одну кнопку/стрелку («Быстрые команды»), которая
раскрывает список по клику и по умолчанию закрыта — на обеих вкладках. Освободившееся
место отдать истории переписки.

## 16. Убрать «Переписать заново» — кнопку и саму функцию

**Решение владельца:** функция не нужна. Все изменения документа делаются через

**Что затрагивает (полный список):**

  `rewriting`, функция `rewriteDocument()`
  (`work/page.tsx:280, 585–591, 1179–1199`);
- эндпоинт `app/api/documents/[id]/rewrite/route.ts` — удалить целиком;
- списание REWRITE при генерации переписанной версии
  (`app/api/versions/[id]/generate/route.ts:53–62`, ветка по флагу
  `aiSettings.rewrite`);
- цена в `lib/token-pricing.ts:19` и её отдача в API
  (`api/wallet/route.ts:25`, `api/documents/[id]/edit-quota/route.ts:25`);
- строка «Переписать заново» в прайс-листе на экране баланса
  (`(app)/balance/page.tsx:183`).

**⚠️ Чего делать НЕЛЬЗЯ (правило проекта №4 — `token_charges` append-only):**
- **не удалять** значение `REWRITE` из enum в `prisma/schema.prisma:399` — на него
  ссылаются уже существующие списания в истории операций пользователей;

То есть удаляем **точку входа** (UI + эндпоинт + новые списания), а исторические
данные и их трактовку сохраняем нетронутыми.
