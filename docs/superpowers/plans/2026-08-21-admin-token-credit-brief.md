# Задание: начисление токенов из админки

> Кому: отдельный чат (НЕ чат по кассе Т-Банка — там занимаются только банком).
> Дата постановки: 2026-08-21. Решение владельца.

## Зачем это нужно

Плату за пользование сервисом **пока не берём**. Все текущие пользователи — друзья
владельца, они тестируют продукт вместе с ним. Сейчас при регистрации выдаётся
500 токенов (`WELCOME_BONUS_TOKENS`), а генерация стоит 100 — friends упираются в
лимит после ~5 документов и тестирование останавливается.

Рассматривали два пути: (а) режим «безлимит» переключателем и (б) ручное начисление
токенов из админки. **Владелец выбрал (б) — только админку.** Причины:

1. Инструмент нужен навсегда, а не только на время беты: вернуть токены за сбой
   генерации, подарить за отзыв, промо-начисление.
2. Друзья тестируют в «боевой» экономике — видно реальное потребление, будет на чём
   строить финальный прайс.

**Режим «безлимит» НЕ делаем** — если ручные начисления станут утомительными,
владелец скажет отдельно.

## Что построить

Экран в админке (владелец = `User.isAdmin`), где можно:

1. Видеть список пользователей: email, текущий баланс токенов, дата регистрации.
2. Начислить пользователю токены. **Значение по умолчанию в поле — 5000**
   (≈50 договоров), владелец может изменить перед подтверждением.
3. Видеть историю начислений: кому, сколько, когда, кто начислил, причина.

## Жёсткие ограничения (нарушать нельзя)

1. **Админ НЕ видит документы пользователей.** Правило №9 в `CLAUDE.md`. На экране
   только email, баланс и денежные операции — ни одного договора, версии или названия
   документа. Не добавляйте «для удобства» ссылки на документы пользователя.
2. **Начисление — это фактически печать денег.** Каждое начисление обязано оставлять
   несмываемый след: кто начислил (id админа), кому, сколько, когда, причина (текст
   от админа). Отмена — только новой операцией, не удалением и не правкой.
3. **Атомарность.** Начисление = одна транзакция БД: инкремент `Wallet.balance` +
   строка `Transaction { type: 'CREDIT', currency: 'TOKEN' }`. Образец уже есть —
   `creditForPayment` в `apps/web/src/lib/payments.ts` и `refundChargeById` в
   `apps/web/src/lib/token-charges.ts`. Ledger `transactions` не переписывается.
4. **Только целые положительные токены.** Никаких дробных, нулевых и отрицательных
   значений (списание админом — отдельная задача, сейчас НЕ нужна). Разумный верхний
   предел на одну операцию (например 1 000 000) — чтобы опечатка не выдала миллиард.
5. **В логи — без ПДн и содержимого** (правило №11): id, суммы, коды. Email в лог не пишем.
6. **Интерфейс на русском.**
7. **Дизайн** — как остальная админка `/admin/ai` и макет `макет/design_handoff_dogovora`.

## Технические зацепки (всё уже существует)

- **Гейт админа:** `requireAdmin(req)` из `apps/web/src/lib/admin-auth.ts` — возвращает
  `{ userId } | null`, при `null` отдавать 403. Образец роута:
  `apps/web/src/app/api/admin/ai/usage/route.ts`.
- **Страница админки:** `apps/web/src/app/(app)/admin/ai/page.tsx` — стиль и структуру
  копировать оттуда.
- **Пункт в сайдбаре для админа:** `apps/web/src/components/layout/app-layout.tsx`,
  функция `SidebarContent` — там уже есть ветка `isAdmin`, добавляется в группу «Настройки».
- **Модели:** `Wallet` (balance `Decimal(10,2)`), `Transaction` (`type CREDIT|DEBIT`,
  `currency TOKEN`), `TokenCharge` (append-only, ТОЛЬКО списания — для начислений НЕ
  использовать). См. `apps/web/prisma/schema.prisma`, секция «Финансы».
- **Кошелёк может отсутствовать** — создавайте через `upsert`, как в
  `creditForPayment` (`wallet.upsert` → `increment`).
- Цены действий — `apps/web/src/lib/token-pricing.ts`, чтобы показать «5000 ≈ 50 договоров».

## Про аудит: нужна новая таблица

`Transaction.description` — свободный текст, для аудита его мало (не видно, КТО начислил).
Предлагается модель вроде `AdminCredit` (append-only): `id`, `adminUserId`, `targetUserId`,
`tokens Int`, `reason String`, `transactionId`, `createdAt`. Плюс миграция.

⚠️ **Осторожно с миграциями:** dev-база общая между чатами, бывали расхождения. Если
`prisma migrate dev` предложит сброс/удаление таблиц — НЕ соглашаться. Рабочий обход,
которым уже пользовались: сгенерировать SQL через теневую базу
(`prisma migrate diff --from-migrations ./prisma/migrations --to-schema-datamodel
./prisma/schema.prisma --shadow-database-url <...>/dogovora_shadow --script`), положить
в новый каталог миграции и применить `prisma migrate deploy`. Перед применением
убедиться, что в SQL нет `DROP`.

## Что НЕ делать

- Не трогать файлы кассы Т-Банка — ими занимается другой чат:
  `apps/web/src/lib/tbank/`, `apps/web/src/lib/payments.ts`,
  `apps/web/src/lib/token-packages.ts`, `apps/web/src/app/api/payments/`,
  и строку `'/api/payments/webhook'` в `apps/web/src/middleware.ts`
  (без неё банк получает 401 и оплаты не зачисляются).
- Не открывать самоначисление пользователям (`POST /api/wallet/topup` намеренно
  отключён и отдаёт 410 — пополнение идёт через кассу).
- Не делать списание/обнуление баланса админом — не заказывали.
- Не менять `WELCOME_BONUS_TOKENS` и цены в `token-pricing.ts`.

## Как проверить, что готово

1. Не-админ на страницу и в API не попадает (403).
2. Начисление 5000 увеличивает баланс ровно на 5000 и создаёт запись в истории
   операций пользователя.
3. Двойной клик/повторная отправка не начисляет дважды.
4. Запись аудита содержит: кто, кому, сколько, когда, причину.
5. Владелец видит новый баланс сразу, без перезахода.
6. `npx tsc --noEmit` и `npx vitest run` из `apps/web` — зелёные.
